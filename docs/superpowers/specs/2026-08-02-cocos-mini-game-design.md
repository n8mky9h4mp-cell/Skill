# Cocos Creator 双端小游戏 Skill 设计

## 1. 目标

新增一个名为 `cocos-mini-game` 的 Agent Skill。用户只需提供一个游戏主题，Skill 即可完成以下工作：

1. 联网调研近期微信小游戏与抖音小游戏的热门品类、题材和代表产品。
2. 根据主题提出 2–3 个适合双端发布的 2D 休闲游戏方向。
3. 在用户选定方向后生成 PRD、开发进度清单和任务拆解文档。
4. 在用户批准文档后，直接创建或修改 Cocos Creator 项目。
5. 完成微信小游戏与抖音小游戏的平台适配、IAA 广告接入、构建和可行的验证。
6. 在开发过程中持续回写进度与任务状态。

Skill 以 Cocos Creator 3.8+ 为版本基线。首版聚焦 2D 休闲小游戏，平台适配层保持与 2D/3D 渲染无关。

## 2. 范围

### 2.1 首版包含

- 近期市场趋势与竞品调研。
- 主题到玩法方案的策划。
- 项目主体、平台账号、合规和发布准备度检查。
- PRD、进度清单与任务拆解。
- 新项目最小初始化或现有项目检查。
- 2D 核心玩法、场景、组件、状态与资源组织。
- 微信、抖音和编辑器模拟环境的平台适配。
- 登录、生命周期、本地存储、分享、系统信息与振动。
- 激励视频、插屏和横幅广告。
- Asset Bundle、分包、双端构建与真机验收指导。
- Web Mobile 预览构建，用于快速验证与小游戏平台无关的核心玩法。
- 调用可用图片生成工具制作角色、场景和 UI 素材。
- 生成可复制到专业音频平台的音效与背景音乐提示词。
- 上线准备清单与首版运营指标定义。

### 2.2 首版不包含

- 支付、内购和混合变现实现。
- 好友排行榜、开放数据域和社交排行实现。
- 3D 游戏专项架构与性能规范。
- 自动发布、平台提审或线上账号操作。
- 自动生成或下载音频文件。
- 基准测试、对照评测和触发描述优化。

支付、排行榜和 3D 能力只在架构边界上避免阻塞未来扩展，不创建空方法、假实现或占位系统。

## 3. 方案选择

采用“单 Skill + 分阶段参考模块”方案。

主入口只保存完整工作流、门槛和模块路由。市场调研、策划、文档、Cocos 架构、平台差异、广告、素材和构建规则分别放入 `references/`，执行到对应阶段时才读取。这能控制上下文体积，同时避免多个 Skill 之间漏触发或交接失败。

不采用以下方案：

- 单一大文档：内容会快速膨胀，平台和阶段规则难以按需加载。
- 多个独立 Skill：复用性更高，但用户只给一个主题时容易漏掉策划、文档或平台适配步骤。

```text
skills/cocos-mini-game/

└── references/

    ├── game-concept.md
    ├── project-readiness-and-compliance.md
    ├── prd-template.md
    ├── project-planning.md
    ├── cocos-architecture.md
    ├── backend-and-data.md
    ├── platform-adapter.md
    ├── wechat-mini-game.md
    ├── douyin-mini-game.md
    ├── iaa-ads.md
    ├── assets-and-audio.md

```

首版不新增脚本。只有后续发现重复且能够确定性执行的校验或生成逻辑时，才考虑加入 `scripts/`。

## 5. 完整工作流

```text
用户主题
  → 联网调研
  → 2–3 个玩法方案
  → 用户选择
  → 项目准备度与合规检查
  → PRD
  → 开发进度清单
  → 任务拆解
  → 用户批准
  → 素材与项目实施
  → 微信/抖音构建验证
  → 持续回写进度
```

### 5.1 第一次确认门槛

联网调研后，Skill 必须给出 2–3 个候选玩法并等待用户选择。在用户选择前，不生成正式 PRD，不创建或修改游戏项目。

### 5.2 第二次确认门槛

用户选定玩法后，Skill 生成三份项目文档并等待批准。在文档获批前，不创建游戏代码和资源。

### 5.3 实施模式

文档获批后默认直接实施。Skill 检查现有项目并遵循其结构；仅在没有项目时创建满足需求的最小 Cocos Creator 3.8+ 项目。缺少本地工具或授权时，完成其他可执行工作并明确记录阻塞，不退化为笼统教程。

### 5.4 输入识别

当用户把目标描述为“微信小程序游戏”时，Skill 先确认其实际目标是微信小游戏还是普通小程序中的轻交互页面。需要 Canvas/WebGL、实时游戏循环、游戏广告或小游戏构建产物时，按微信小游戏处理，避免采用不匹配的 WXML 页面架构。

## 6. 市场调研与玩法推荐

调研默认关注最近 6–12 个月，并记录数据发布日期与实际统计周期。来源优先级如下：

1. 微信、抖音、Cocos 等平台或厂商的官方文档与报告。
2. 游戏产业机构、公开课和具有明确统计口径的行业报告。
3. 可查看更新时间的小游戏榜单与投放数据。
4. 媒体和营销文章，仅用于交叉验证，不作为单一结论来源。

每个候选玩法包含：

- 一句话定位与核心循环。
- 目标用户和单局时长。
- 主题与玩法的结合方式。
- 与近期热门产品的相似点和差异点。
- IAA 广告点及其对体验的影响。
- 开发复杂度、素材成本和主要风险。
- 推荐理由与不推荐条件。

输出必须区分来源支持的事实和基于事实的推断。不能仅因某个品类热门就机械套用，还要评估主题契合度、同质化风险和首版开发成本。

可用参考入口包括：

- [Cocos Creator 3.8 多平台发布](https://docs.cocos.com/creator/3.8/manual/en/editor/publish/)
- [Cocos Creator 3.8 小游戏发布](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/publish-mini-game.html)
- [DataEye 年度报告入口](https://www.dataeye.com/media-center.html?type=YEAR)

## 7. 项目文档

选定玩法后，在目标游戏项目中生成：

```text
docs/game/
├── PRD.md
├── progress.md
└── tasks.md
```

### 7.1 `PRD.md`

包含产品目标、目标用户、核心循环、玩法系统、界面流程、基础数值、IAA 广告设计、素材需求、双端要求、技术栈、项目目录结构、风险、验收标准和调研来源。立项字段至少覆盖横竖屏、单手操作、单局时长、单机或联网、存档方式、目标年龄层和是否需要后端。

技术栈章节至少说明：

- Cocos Creator 基线版本与 TypeScript 使用范围。
- 实际需要的引擎模块、物理或碰撞方案和资源管理方式。
- 微信、抖音及 Web Mobile 构建目标。
- 第三方依赖、用途、版本约束和引入理由；没有必要时保持零额外依赖。
- 后端、存储、CDN、数据统计等可选能力是否启用，以及不启用的理由。
- 本地开发、构建、调试和真机验证所需工具。

目录结构章节应给出目标项目树，并为每个主要目录标明职责。目录只规划已批准功能需要的内容，至少区分场景、脚本、预制体、图片、音频、配置和平台适配代码。已有项目优先沿用现有结构，只规划本次需要新增或调整的部分，不为了匹配模板而重排整个项目。

### 7.2 `progress.md`

按阶段维护待开始、进行中、已完成和受阻事项。每完成一个可验证任务后立即更新，确保文档反映真实状态。

### 7.3 `tasks.md`

将工作拆成可独立完成和验证的小任务。每项写明目标、依赖、产物和完成条件，避免用“完成游戏”等不可验证的大任务替代拆解。任务涉及的文件与目录应能追溯到 PRD 中批准的项目结构。

三份文档必须使用相同的功能名称、技术栈、目录结构和范围。修改 PRD 范围或目录规划时，同步调整进度与任务；实施中确需偏离时，先在 PRD 中记录原因和新结构。

### 7.4 MVP 收敛规则

首版优先建立一条可重复游玩的完整闭环：启动、进入游戏、核心操作、成功或失败、结算、再次开始。对于个人或小团队的新项目，默认优先评估竖屏、单手操作、2D、单局 1–3 分钟、无需实时联机的方案，但该组合是推荐启发式，不是强制模板。

首版不应在核心玩法未经验证前加入大型 RPG、实时对战、复杂社交、商城或大量活动。任何扩展都需要能追溯到已批准的 PRD。

### 7.5 项目准备度与合规检查

在写 PRD 时同步建立用户操作清单，覆盖平台主体与账号、App ID、开发者工具、备案或审批咨询、隐私说明、未成年人保护、广告规范、客服渠道，以及图片、音乐、字体、角色和代码的授权证明。

这些要求具有地域、主体、玩法和时间敏感性。Skill 必须在实际项目中查询当前官方规则，记录查询日期和来源，不能把历史对话或二手文章当作最终法律结论。无法确定时标记为需平台、发行或合规专业人员确认，不擅自承诺可以上线。

客户端不得保存 AppSecret、支付密钥、服务端签名密钥或其他长期秘密。

## 8. Cocos 项目架构

项目按职责分成三层：

```text
游戏玩法与界面
      ↓
统一平台服务接口
      ↓
微信实现 / 抖音实现 / 编辑器模拟实现
```

游戏逻辑不得散落调用 `wx` 或 `tt`。统一平台服务负责环境识别、能力检测和平台结果归一化，首版覆盖：

- 登录与会话状态。
- 本地存储。
- 分享。
- 激励视频、插屏和横幅广告。
- 系统与设备信息。
- 振动反馈。
- 前后台生命周期。

编辑器模拟实现用于本地预览，但模拟返回值必须可识别，不能让假登录或假广告被误认为真实平台成功。

玩法层按 PRD 的实际需要组织场景、组件和纯逻辑模块。不预建通用框架、不引入无需求依据的依赖，也不为单次使用设计复杂抽象。

最小场景流通常包含启动、主界面、游戏、结算和设置；实际项目只创建 PRD 需要的场景。开发期间保留 Web Mobile 预览目标，用于快速验证核心玩法；平台登录、广告、分享和生命周期仍以微信、抖音开发者工具及真机结果为准。

### 8.1 后端决策门槛

默认先采用纯客户端和平台本地能力完成首版。只有 PRD 明确需要跨设备云存档、多人或实时交互、服务端权威奖励、远程配置、账号体系或运营后台时，才提出后端方案并再次确认范围。

一旦引入后端，服务端不能直接信任客户端提交的分数、奖励或广告结果，应考虑会话校验、参数边界、幂等、防重复领取、频率限制和异常记录。后端技术栈由目标项目决定，Skill 不固定为某一种语言或数据库。

## 9. IAA 广告规则

- 激励视频只有在完整播放并收到平台成功回调后才能发放奖励。
- 关闭、加载失败、展示失败或回调状态不明时不得发放奖励。
- 防止重复回调导致重复奖励。
- 广告不可用时不能阻断核心游戏流程，应提供明确、轻量的反馈。
- 插屏只在自然停顿点触发，例如结算或章节切换。
- 横幅不能遮挡核心操作区，并应适配安全区域。
- 广告对象的创建、加载、展示和销毁遵循各平台生命周期。

首版以 IAA 为明确商业目标，不实现支付。

## 10. 图片与音频

### 10.1 图片

优先调用当前环境可用的图片生成工具，制作角色、场景、UI、图标和必要的宣传素材。生成前统一确定风格、尺寸、透明背景、切图方式和命名规则，避免逐张生成造成风格漂移。

图片工具不可用时可使用程序绘制或临时占位素材验证玩法，但必须在进度文档中标记，并提供替换清单。占位素材不能影响核心玩法验收。

### 10.2 音频

不自动生成或下载音频文件。输出音频提示词清单，每项包含：

- 使用场景和触发时机。
- 音频类型、建议时长和是否循环。
- 情绪、节奏、乐器或声音材质。
- 音量层级和与其他声音的关系。
- 需要避免的元素。
- 建议文件名和目标资源路径。

用户在专业平台生成音频后，可由 Skill 按清单接入项目。

## 11. 验证与失败处理

开发循环固定为：领取最小任务、标记进行中、实施、验证、回写状态、进入下一任务。

验证分为四层：

1. 纯逻辑验证：数值、状态机、奖励条件和存档转换尽量与 Cocos 节点解耦。
2. 编辑器验证：场景可加载、组件引用完整、核心循环可操作。
3. 双端构建验证：生成微信和抖音小游戏产物，检查配置、资源、分包和明显体积问题。
4. 真机验收：登录、分享、广告、生命周期和设备能力在对应开发者工具或真机验证。

测试矩阵根据 PRD 裁剪，但至少考虑：

- 设备：不同屏幕比例、安全区域、低端 Android 和主流 iPhone。
- 网络：弱网、断网、超时、重连和资源加载失败。
- 性能：启动时间、帧率、内存、Draw Call、纹理体积、场景切换和长时间运行。
- 生命周期：前后台切换、恢复、重复进入和版本更新后的存档兼容。
- 广告：加载失败、中途关闭、完整播放、重复回调和展示频率。

缺少 Cocos Creator、开发者工具、App ID、网络或平台权限时：

- 不声称相关验证已通过。
- 继续完成不依赖该条件的工作。
- 在 `progress.md` 中记录阻塞原因、影响范围和恢复条件。
- 给出最短、明确的人工验证步骤。

## 12. 完成标准

- PRD 中定义的核心玩法能够完整游玩。
- 微信和抖音构建成功，或外部阻塞被准确记录。
- 广告奖励不存在失败发放和重复发放。
- 平台 API 不侵入玩法层。
- 图片素材已经落盘，或占位替换项被明确记录。
- 图片、字体、代码和后续音频均有明确来源或授权记录。
- 音频提示词清单完整交付。
- Web Mobile 核心玩法预览通过，或阻塞原因被记录。
- `PRD.md`、`progress.md` 和 `tasks.md` 与实际实现一致。
- 没有遗留未完成标记或未经说明的占位行为。

## 13. 发布与运营准备

Skill 不自动提交审核或发布，但应生成与项目范围匹配的发布准备清单，包括游戏资料、玩法说明、截图、隐私与用户协议、版权授权、测试入口、广告说明、构建版本和人工真机验收项。两端的具体表单、资质和审核规则在执行时查询官方资料。

PRD 同时定义首版需要观察的指标，至少包括新增用户、次日留存、单局时长、关卡通过率、广告加载成功率、激励完成率、崩溃率和资源加载失败率。上线后的迭代遵循“数据观察、定位流失点、修改、内部验证、灰度或小范围观察、再扩大”的循环。

## 14. 仓库集成

实现阶段新增 `skills/cocos-mini-game/` 后，同步更新：

- `README.md` 中的 Skill 数量、徽章和索引。
- `llms.txt` 中的 Skill 数量、导航和参考文件索引。

实现验证至少包括：

- `SKILL.md` frontmatter 的 `name`、`description` 与目录名一致。
- 所有新增链接的目标文件存在。
- 新增文件不含未完成标记或临时说明。
- `git diff --check` 无空白错误。

## 15. 测试取舍

用户明确要求首版不运行 Skill 基准测试、对照评测或描述触发优化。因此实现阶段只进行仓库结构、内容一致性和链接等静态验证，不创建 `evals/` 或评审页面。
