# `write-wechat-articles` Skill 设计

> 后续已增加 HTML 源码与富文本复制预览，见 [微信公众号 HTML 富文本交付设计](2026-07-31-write-wechat-html-copy-design.md)。

## 目标

创建一个面向中文技术与 AI 创作实践公众号的写作 Skill。它帮助开发者和 AI 创作者把主题、资料、提示词或草稿整理成简洁、可靠、适合手机阅读的公众号文章。

默认生成 Markdown 原稿、公众号排版稿和必要的运营素材，并自动保存到当前工作区。文章以讲清核心问题所需的最短长度为准，不做教科书式展开。

## 使用场景

Skill 应覆盖以下主要文章类型，并根据选题自动选择结构：

- 实战教程与踩坑记录
- 技术原理与源码分析
- 故障复盘
- 工具、框架或 AI 产品评测
- AI 漫剧、AI 视频与 AI 音乐创作实践
- 提示词分享

技术文章默认面向具备基础知识的开发者。AI 创作文章默认面向已经使用过相关工具的创作者。文章不重复解释行业常识或工具入门操作，但应说明理解结论所必需的概念、限制和取舍。

默认采用一线实践者分享口吻：专业、直接、有实践判断，不写成产品宣传稿。

Skill 不覆盖情感、生活、娱乐资讯等泛公众号写作。

## 目录结构

```text
skills/write-wechat-articles/
├── SKILL.md
└── references/
    ├── article-patterns.md
    ├── research-policy.md
    ├── wechat-formatting.md
    └── quality-checklist.md
```

不创建 `agents/openai.yaml`、转换脚本、README 或其他辅助文件。

## 文件职责

### `SKILL.md`

作为唯一入口，负责：

- 识别用户的写作目标和已有材料
- 判断文章类型
- 调用资料检索、写作、压缩和核验流程
- 按固定顺序组织最终交付内容
- 在资料不足时停止猜测并说明缺口

核心流程保持简短，详细规则通过 `references/` 按需加载。

### `references/article-patterns.md`

定义教程、原理分析、故障复盘、工具评测、AI 创作实践和提示词分享的最小文章骨架。

这些骨架只约束信息闭环，不规定统一开头、固定小标题数量或相同段落节奏。执行者应根据主题删除不需要的章节，避免机械套模板。

### `references/research-policy.md`

定义资料优先级和事实核验规则：

1. 官方文档、模型说明、标准、规范
2. 官方源码、变更记录、发布说明
3. 原始论文或作者发布内容
4. 可靠的二手技术资料和实际案例

检索时应优先使用一手资料。涉及 AI 工具时，应核对模型、版本、平台和功能状态。文章必须区分已实际测试、依据资料整理、建议尝试、合理推断和作者判断，不得编造版本信息、性能数据、生成结果、引用或实践经历。

### `references/wechat-formatting.md`

定义适合公众号移动端阅读的排版规则，包括：

- 使用少而明确的标题层级
- 控制段落长度，每段表达一个重点
- 保持代码块完整，避免过宽示例
- 谨慎使用加粗、引用、列表和分隔
- 为必要的配图保留明确占位与说明
- 保持正文图片占位符与文末配图清单编号一致
- 保持 Markdown 原稿和公众号排版稿内容一致

排版采用克制的技术编辑风格，避免密集装饰、通用 AI 紫色光效、虚假界面和模板化视觉语言。

### `references/quality-checklist.md`

定义技术正确性、内容效率、移动端可读性和文风真实性检查，并包含各文章类型的最低验收标准。

## 工作流程

1. 读取用户提供的主题、资料、代码或草稿。
2. 判断文章类型、核心读者目标和需要解决的问题。
3. 主动检索官方文档、模型说明、源码、标准、论文等一手资料。
4. 提炼一个核心结论，删除与结论无关的背景。
5. 选择最合适的最小文章结构。
6. 优先写结论、关键代码或提示词、实际结果、限制和取舍。
7. 核验事实、模型、版本、平台、命令、代码行为和引用。
8. 压缩文字，删除重复解释、空泛过渡、常识性展开和总结式复述。
9. 判断图片是否有助于解释内容，只为必要图片设置占位符。
10. 生成 Markdown 原稿、公众号排版稿、配图清单和运营素材。
11. 按质量清单完成最多两轮内部校验。
12. 将文章与素材说明自动保存到当前工作区。
13. 在对话中返回简短摘要、文件链接和校验结果。

若两轮后仍缺少关键资料，应明确列出缺口，不得继续扩写或猜测。

## 输入处理

Skill 应支持以下输入形态：

- 只有一个技术主题
- 主题加目标或观点
- 原始笔记、代码、日志或故障记录
- AI 创作流程、参数、提示词或生成结果
- 用户提供的截图、生成结果、流程图或其他图片
- 已完成的文章草稿
- 官方文档、源码仓库、论文或网页链接

当用户只给出主题时，默认主动研究后直接成稿，不要求用户先确认提纲。只有缺失信息会实质改变技术结论时，才提出一个简短问题。

## 默认交付格式

每次按以下顺序输出：

1. **标题候选**：3 个。准确兑现正文，不使用夸张数字、悬念欺骗或“彻底讲透”等标题党表达。
2. **公众号摘要**：约 60-100 字，直接说明文章解决的问题和读者收益。
3. **Markdown 原稿**：使用标准标题、代码块、链接、图片占位和引用，便于修改与版本管理。
4. **公众号排版稿**：内容与 Markdown 原稿一致，只调整为适合手机阅读的富文本结构。
5. **配图清单**：仅在正文需要图片时提供，列出位置、用途、类型、建议尺寸、图片说明和生成提示词。
6. **封面图提示词**：1 条简洁提示词，使用克制的技术编辑视觉。
7. **文末互动语**：1 句与文章主题直接相关的问题，不要求点赞、在看或转发。

默认不输出写作过程、长篇资料综述或逐条写作解释。

提示词文章默认提供可直接复制的完整提示词。使用 `[角色设定]`、`[镜头运动]`、`[音乐风格]` 等明确占位符标记可替换内容，并注明适用工具或模型。只解释影响结果的关键变量，不逐句拆解或复述提示词。

## 自动保存

文章通过质量检查后，默认保存到执行任务时的当前工作区：

```text
articles/
└── YYYY-MM-DD-短标题/
    ├── article.md
    ├── wechat.md
    └── assets.md
```

文件职责：

- `article.md`：保存标题候选、公众号摘要、Markdown 正文和参考资料。
- `wechat.md`：保存可复制到公众号编辑器的完整排版稿和文末互动语。
- `assets.md`：保存封面图提示词、正文配图清单和素材库替换说明。没有正文配图时，仍保留封面图提示词。

目录名中的短标题从最终推荐标题提取。删除 `\ / : * ? " < > |` 等文件系统不安全字符，将连续空格替换为连字符，并截取前 40 个字符。清理后为空时使用 `未命名文章`。

若目标目录已存在，依次使用 `-2`、`-3` 等后缀创建新目录，不得覆盖旧文章。

若当前工作区不可写，不得将文章保存到 Skill 安装目录。此时退回对话输出完整文章，并明确说明失败原因和未保存状态。

保存成功后，对话只返回文章摘要、三个可点击文件链接和校验结果，不重复输出完整文章。

## 图片素材处理

默认不自动生成图片，也不声称已经将图片上传到微信公众号素材库。用户负责上传素材并替换占位符。

正文只在图片能解释流程、证明结果或帮助比较时使用图片。没有明确作用时，不输出占位符或配图清单。

统一使用可见占位符：

```text
【配图 01｜用途｜建议比例｜替换为公众号素材库图片】
```

Markdown 原稿和公众号排版稿必须使用相同的图片编号和插入位置。文末配图清单为每张图片提供：

- 插入位置
- 内容用途
- 素材类型
- 建议尺寸或比例
- 图片说明
- 可选的图片生成提示词

用户已提供图片时，优先使用现有素材，并给出必要的裁剪、排序和图片说明建议。技术截图、效果对比和生成结果必须使用真实素材，不使用 AI 生成的假界面或假结果代替证据。AI 生成图片仅用于封面或装饰插图。

使用网络图片时，应注明来源并提示授权、转载和版权风险。

## 文章类型要求

### 实战教程

- 尽快说明最终要完成什么
- 给出必要前提和最短可执行步骤
- 使用完整、自洽的代码或命令
- 只解释关键步骤
- 说明高频失败原因和解决方式

### 原理分析

- 先给核心机制或结论
- 只展开支撑结论的关键链路
- 使用必要的代码、流程或示例
- 明确适用边界，不扩展成百科全书

### 故障复盘

- 说明现象与影响
- 给出定位过程中的关键证据
- 区分直接原因和根因
- 说明修复方案和预防措施
- 不虚构时间线、指标或线上数据

### 工具评测

- 说明测试条件和比较维度
- 展示真实能力、限制与使用成本
- 说明适用和不适用场景
- 不复述厂商宣传，不写成软文

### AI 创作实践

- 直接说明创作目标和最终工作流
- 给出关键设置、完整提示词和必要参数
- 展示结果差异时说明测试条件
- 不讲注册、界面按钮等基础操作，除非它会影响结果
- 说明模型能力边界和版权、肖像、声音克隆等风险

### 提示词分享

- 标明适用工具、模型和用途
- 提供一个可直接复制的完整提示词
- 使用明确占位符标记可替换变量
- 只解释关键变量和使用限制
- 不把单次结果描述为稳定能力

## 异常与不确定性处理

- 资料来源相互冲突时，优先采用最新的一手资料，并简要指出差异。
- 无法确认版本或行为时，明确标记未确认项，不使用模糊措辞掩盖。
- 无法运行示例时，不宣称已经验证；改为说明静态检查范围。
- 未实际使用提示词生成结果时，标记为“依据资料整理”或“建议尝试”。
- 用户材料包含敏感信息时，不在文章中复现密钥、内部地址或个人数据。
- 涉及角色、音乐或素材时，提醒版权、肖像、声音克隆和平台规则风险。
- 无法确认网络图片授权时，只保留素材建议，不直接使用该图片。
- 选题过大时，收窄到一个能完整讲清的核心问题，必要时建议拆成系列。

## 质量验收

### 技术正确性

- 版本、模型、平台、API、参数、命令和代码行为有可靠依据。
- 代码示例完整、自洽，必要时包含预期结果。
- 事实、推断和个人判断可以明确区分。
- 提示词完整、变量清楚，并说明适用工具或模型。
- 不编造测试结果、生成结果、性能数字、实践经历或引用。

### 内容效率

- 开头尽快进入问题和结论。
- 每段只表达一个重点。
- 删除重复结论、空泛铺垫、常识性解释和无意义金句。
- 不为了篇幅增加背景、术语或总结。

### 公众号可读性

- 标题层级少而明确。
- 段落适合手机屏幕阅读。
- 代码行宽和示例规模可控。
- 不连续加粗，不堆叠列表，不依赖装饰性符号制造层次。
- 图片编号、占位位置和配图清单一一对应。
- 每张图片都有明确用途，不为丰富版面堆图。

### 文风真实性

- 使用一线实践者的直接表达。
- 给出真实限制、适用边界和技术取舍。
- 避免营销腔、AI 腔、故作深刻和强行幽默。
- 不使用破折号作为装饰性写作手段。

## 验证方案

实现后至少使用六类提示进行前向测试：

1. 仅提供一个主题的实战教程
2. 提供官方链接的原理分析
3. 提供日志和代码片段的故障复盘
4. 提供两个工具名称的技术评测
5. 提供一个目标的 AI 漫剧提示词分享
6. 提供一个创作需求的 AI 音乐实践文章

自动保存规则还应覆盖：

1. 首次保存时创建标准目录与三个文件
2. 同名目录存在时追加数字后缀
3. 无正文配图时仍生成包含封面提示词的 `assets.md`
4. 当前工作区不可写时退回对话输出且不写入 Skill 目录

每个结果按 `quality-checklist.md` 检查：

- 是否选择正确的文章结构
- 是否优先引用一手资料
- 是否存在未经证实的事实
- 提示词是否完整、变量是否清楚、适用工具是否准确
- 是否夸大提示词的稳定性或可复现性
- 图片占位符与配图清单是否一致
- 是否把虚构图片、假界面或生成插图当作事实证据
- 是否保持简洁
- Markdown 与公众号排版稿是否内容一致
- 运营素材是否克制且与正文匹配
- 三个保存文件是否职责清楚、内容完整
- 是否避免覆盖同名文章

前向测试不修改生产系统，不发布文章。发现问题后最多修订 Skill 两轮，仍未解决的项目应记录为已知限制。
